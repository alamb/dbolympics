# Query generation: the simulated analytics department

The benchmark's 409 queries come from one run of this role play, `run6`; its parameters and
archive are in [runs/README.md](../runs/README.md). `roleplay/` holds the prompts as they were
for that run.

## Idea

The benchmark queries are written by LLM agents (Sonnet) role-playing a real company.
They never learn that we are after the SQL. The SQL is a by-product of them trying to
understand the business, which gives realistic intent, realistic query shapes, and a
natural-language lineage for every query.

Each track is one leader and their team: the **manager** asks broad questions, the **analyst**
turns them into concrete data questions for a summary report, and **engineers** turn each
data question into SQL, in varied styles.

## Analysis loops

Analysts read the results and follow up: overview -> something looks off (e.g. the UK
in November) -> drill down -> test a hypothesis -> drill down again. These chains are part
of the workload: queries get more selective and more complex along a chain.

For this to work the simulator plants **stories** in the data (incidents, business
dynamics, data-quality problems). The story list is secret from the agents; afterwards we
can also check which stories they found. Stories must hold at every scale factor: named
entities, literal values and incident windows are fixed, only volumes scale.

## Queries are expensive

The agents believe running a query is costly, so they pack questions into few, dense queries
instead of spamming probes. The framing:

- the warehouse is shared and metered; each executed query is billed to the department;
- execution is an overnight batch: one round of the loop = one day, the report is due
  this week;
- fixed budgets: a few query slots per analyst per night, 4 nights; failed queries cost too;
- compiling / dry-running against the schema is free, execution is not;
- results come back as printed reports, capped at ~50 rows.

Scarce queries should produce *dense* queries (one question answered in depth), not
*bundled* ones (unrelated questions glued together with UNION ALL, NULL-padded columns,
independent scalar subqueries side by side, 40-column pivots). The rules target what a
report is, not how many queries are run:

1. **One request = one question = one printed report**: a title, the analyst question it
   answers, the expected columns; one table at a single grain (every row is the same kind
   of thing: a country, a week, a merchant; columns are measures about it).
2. **The page has a width**: ~10 columns, ~50 rows.
3. **Bundles are bounced.** The handbook says data engineering reviews every request and
   bounces bundled ones, and that a bounced request still uses its slot. There is no reviewer
   agent: the warehouse bounces mechanically (one statement, at most 12 columns) and only
   records hidden warnings for signs of bundling (see "The warehouse").
4. **Nothing else is measured**: the agents' only goal is a good report for the manager
   under the budget. No visible query score, no reward for complexity.

Allowed and wanted: dense single-grain queries, e.g. per country and month: orders,
revenue, refund rate, late-delivery share, ticket rate, and the same month last year.

The house SQL standards ask for standard SQL with no hints about constructs, a fixed
reporting date instead of CURRENT_DATE, and small, report-ready results with deterministic
ORDER BY and tie-breaks. Portability to other engines is the canonical text's job (below).

## What the agents see

Everything the agents see is in `roleplay/`; the orchestrator sends nothing else, and refuses
to start if one of these files contains a revealing word ("benchmark", "story", "simulated",
"synthetic", ...).

- `company.md`: the backstory (section 1 of [WORLD-MODEL.md](WORLD-MODEL.md)) under the
  Tidewick name.
- `handbook.md`: the budget, the report rules and the house SQL standards.
- `schema.md`: the table catalog, generated by `tools/roleplay_docs.py` from the schema
  metadata: 212 non-lookup tables with descriptions, columns, foreign keys, allowed codes and
  unique keys, benchmark wording scrubbed out.
- `personas.json`: 18 leaders, 18 analysts (one per leader, each with a working style) and
  6 engineer SQL styles (CTE layers, nested subqueries, window functions, old-school join
  chains, BI-tool-generated, minimal).
- `situations.json`: 35 business situations (below).
- `roles/*.md`: the instructions per role, filled in with the persona.

The manager remits describe the job, not the planted stories.

## The organisation and how it talks

A small organisation with only "core" functions anchors on the core tables and leaves whole
areas untouched (trial runs used fewer than half the tables), so the 18 leaders cover every
area, each with a `reports_to` line:

- the CEO, with CFO, COO, growth, merchant success, product, data, CISO, VP Platform
  Engineering and Head of B2B Commerce reporting to them;
- to the CFO: risk, Data Protection Officer, Head of Pricing & Promotions;
- to the COO: customer experience, Head of Merchandising, Director of Fulfilment Operations;
- to growth: Head of Lifecycle Marketing; to customer experience: Support Operations Manager.

Three mechanisms let questions span roles:

1. **Co-owner notes.** When a situation with co-owners arrives, each co-owner writes their
   own short note to the lead's analyst (`roles/coowner.md`). The analyst gets all the notes
   and has to reconcile the priorities.
2. **The analytics channel.** At the end of each week every analyst posts 2-3 headline
   findings (`roles/analyst-headlines.md`, structured). Next week every analyst reads the
   whole digest in their Monday opening, which makes cross-domain follow-ups possible.
3. **The hierarchy reads downward.** In week 2 and later, a leader's follow-up note shows the
   headlines of the teams of their direct reports, so the CEO sees those of the CFO, COO and
   so on.

Weeks run in lockstep: week w+1 starts for all tracks once every track has finished week w.

## Situations

If every manager is "new, wants to understand the area", questions stay narrow and
function-bound. Wide analysis comes from questions whose unit is an outcome or an entity:
root cause of a metric, fully loaded unit economics, end-to-end journeys and post-mortems,
reconciliation and audit, account 360 reviews and due diligence, launch readouts with
guardrails.

`roleplay/situations.json` holds 35 ordinary business situations of these kinds, each with a
lead manager and optional co-owners (e.g. the board asks for unit economics, the year-end
audit, a peak post-mortem, a churn task force, a security questionnaire, metric
certification). They add to onboarding rather than replace it, as in a real company:

- Each week a track without a situation gets one with probability `--situations` (default
  0.5), drawn by seed from its manager's situations; at most one per track. With 2 weeks
  and 0.5, about three quarters of the tracks get one.
- Arriving in week 1, the note uses `roles/manager-situation.md` instead of plain
  onboarding; arriving later, it comes on top of the reply to the memo.
- The situation id is in the lineage of every request made after it arrived.

Situations are generic: no merchants, dates or incidents. Some naturally touch areas where
stories are planted (a security questionnaire, a tax review), as real business events would.

## A week of a track

1. **Manager note.** The manager writes 3 to 5 broad questions.
2. **Analyst nights** (`--nights`, default 4). Each night the analyst hands in up to
   `--slots` (3) requests as strict structured output: title, question, grain, columns,
   details and builds_on.
3. **Engineers.** Each request goes to an engineer, chosen deterministically per request, in
   a fresh conversation with the tools `dry_run` (free, up to 12 steps) and `submit`. It ends
   after `submit` or `--engineer-turns` (default 25; none for Codex), with one nudge if
   nothing was submitted.
4. **Reports.** The warehouse runs each submitted query; the printed reports, plus any
   engineer note, return to the analyst.
5. **Memo.** After the last night the analyst writes the memo to the manager.
6. **More weeks** (`--weeks N`). The manager replies to the memo with follow-up questions.

Managers and analysts keep one conversation per track across nights and weeks.

## The warehouse

- `dbolympics load <dir> <db>` builds a DuckDB file from a generated dataset.
- `dbolympics query --db <db> --sql <file|-> --title --question [--dry-run] [--log] [--tags]`
  handles one request, opening the database read-only so requests can run in parallel.
- It parses the SQL with `json_serialize_sql`, rejects anything that is not exactly one
  statement and records the base tables, excluding CTE names. It also rejects functions it
  pretends not to have (`generate_series`, `range`) with an engine's unknown-function error.
  It defines `json_value` the standard way, because DuckDB's own returns JSON-quoted strings
  and comparisons would silently match nothing.
- A dry run executes the query against an empty copy of the schema (`<db>.empty.duckdb`), so
  it catches errors `EXPLAIN` misses (such as casts that fail only at run time), reports the
  output columns and bounces more than 12. It never reads or shows data, and stops after 2
  minutes; a report query is cancelled after `--query-timeout` (default 600 s).
- A real run bounces more than 12 columns and prints at most 50 rows with right-aligned
  numbers and a row-count footer.
- Hidden **warnings**, never bounces: a UNION whose branches share no tables; 2 or more
  scalar subqueries in a select with no FROM, or 3 or more in any select; 2 or more columns at
  least 80% NULL. These do not bounce because they also hit legitimate reports (detail
  reports at the end of drill-downs, correlated per-row subqueries). Warnings go to the
  lineage record and the viewer; the agents only get the report.
- Every request appends one JSON line to `--log`: title, question, SQL, tags, verdict,
  reasons, tables, columns, rows and elapsed time.

## Running the role play

```sh
python3 tools/roleplay.py --db tmp/sf1.duckdb --out tmp/roleplay/run1 [--managers ceo,ops] \
    [--weeks 2] [--seed 5] [--parallel 3] [--backend claude|codex|api] [--mock]
```

Backends (`tools/roleplay_llm.py`): `claude` (default; headless Claude Code on the logged-in
subscription), `codex` (headless `codex exec`), `api` (any OpenAI-compatible
`/chat/completions`; `--api-base`, `--api-key-env`, `--model`). The CLIs get the warehouse
tools (`tools/roleplay_tools.py`) through the MCP server `tools/roleplay_mcp.py`. `--mock`
replaces the model with canned answers that still drive the real tools and warehouse. Failed
calls (e.g. on a usage limit) are retried with backoff up to 15 minutes.

Isolation: the agents see only a system prompt built from `roleplay/`, their conversation
and, for engineers, `dry_run` and `submit`. The CLIs run in an empty directory outside the
repository with user settings, built-in tools, shell and web access switched off. Codex is
not fully isolated when `/etc/codex/requirements.toml` demands permission profiles from the
user's `config.toml`; run6 used the Claude backend.

The output directory holds `lineage.jsonl` (the query pool), `dry_runs.jsonl`, per track the
notes, plans, printed reports, memos, prompts and transcripts, `usage.json`, and `index.html`
(the run as a page, from `tools/roleplay_viewer.py`); see the archived run in
[runs/](../runs/README.md), whose transcripts have the account e-mail and home folder
redacted. `tools/roleplay_stats.py <run>` counts SQL features, joins and table coverage.

## Catalog and traceability

The end product is not a list of queries but queries that can be traced back to the
conversations that produced them. There are three layers, linked by a **trace key** per
original query: `<run>/<team>/w<week>-n<night>-r<request>`, e.g. `run6/ops/w2-n3-r1`.

1. **Archive** (`runs/`, see [runs/README.md](../runs/README.md)): the raw truth. Everything
   else is derived from it and points back into it.
2. **Catalog** (`workload/catalog.json`, built by `tools/catalog.py`): one entry per printed
   query of the run, with ids `q001` to `q409` in the order the queries were asked. Each query
   is profiled on SF1 with `dbolympics profile` (plan, result size, run time, fingerprints of
   the whole result and of each column). An entry records:
   - **Trace:** the trace key and the files of its conversation inside the archive.
   - **SQL:** the original SQL, the title and question of the request, the tables.
   - **Family:** the same tables, join conditions and aggregate functions in the optimised
     plan. In run6, 4 families have 2 or more members.
   - **Related:** the same tables and joins only (55 queries).
   - **Shared measures:** identical numeric result columns that are not ids or date parts,
     with the matching column names (60 queries).
   - **Rewrite class:** at least 2 shared measures covering 80% or more of each side, or the
     whole result equal (1 class of 2 queries).
   - **Same text:** none.
   - **Builds on:** earlier requests a request names as its basis (317 of 409; inferred from
     titles).
3. **Website** (`site/queries.py`), generated from catalog and archive. A query page shows
   the SQL and, as a timeline, the conversation that led to it: the situation, the leader's
   and co-owners' notes, the analyst's plan for that night, the engineer's dry runs and
   submit, the printed report as the analyst saw it, where the memo cites it, and follow-up
   requests and pickups through the analytics channel.

Families are rough: they mix questions over the same tables; the same computation written
differently shows only in shared measure columns.

**Rules for the sources:**

- **Many sources per query.** Every catalog entry lists *all* the original queries it
  stands for as trace keys, each with its relation:
  - `original`: the representative;
  - `same-text`: identical after normalising constants and formatting;
  - `same-result`: different SQL, same result;
  - `merged`: by hand, with a note.
- **Merging never deletes.** Merging B into A moves B's sources to A and leaves a forward
  reference in place of B's id. Old ids and links keep working.
- **Derivations are steps.** Parameterising, translating to another engine or changing
  constants are recorded as steps with notes, so the chain back to the original SQL and its
  conversation never breaks.
- **Inferred links are marked.** Links resolved from free text (`builds_on` titles, memo
  citations of report titles) are matched within the same track and marked as inferred.
- **Reports keep their time.** A printed report reflects the data the analyst queried. The
  site shows it as the analyst saw it.

## Canonical queries

The benchmark should be easy for any database to run. Each catalog query therefore has one
canonical text, `workload/queries/qNNN.sql`, built by `tools/canonical.py` from the original
SQL. Every step is recorded per query in `workload/queries/derivations.json`, so the chain
back to the original SQL never breaks. In order:

1. **Manual edits** (`workload/queries/edits.json`): exact text replacements for single
   queries, each with a note. Examples: `DISTINCT ON` becomes `ROW_NUMBER() ... = 1` (q175,
   q210, q359); `unnest(ARRAY[...])` in a select list becomes a `VALUES` list (q082); an output
   alias that reuses the name of an input column the same block still uses is renamed (q019,
   q090, q121, q255, q332, q333, q348); `->>` becomes `JSON_VALUE` (q175, q399).
2. **Hard translations**, for every database; they cannot affect performance:
   - `x::t` becomes `CAST(x AS t)`;
   - `LIMIT n` becomes `FETCH FIRST n ROWS ONLY`;
   - `date_part('f', x)` becomes `EXTRACT(f FROM x)`;
   - `DATE(x)` becomes `CAST(x AS DATE)`;
   - a date string compared with a column becomes a `DATE` literal;
   - a selected bare `t.col` gets `AS col`, the name SQL gives it anyway.
3. **Determinism fixes** (`workload/queries/determinism.json`, see below): exact
   replacements that append tie-breakers.
4. **Numeric normalization** (`workload/queries/numerics.json`; rules and reasons in
   [NUMERICS.md](NUMERICS.md)): no `ROUND` and no bare `NUMERIC` casts; exact arithmetic in
   one type, `NUMERIC(18,6)`; fractions become integers only by `FLOOR`/`CEIL`; seconds
   between timestamps and currency conversions are cast to `NUMERIC(18,6)`.
5. **Null order:** every sort key without `NULLS FIRST` or `NULLS LAST` gets the order of the
   reference results (`NULLS LAST` ascending, `NULLS FIRST` descending), which the standard
   leaves to the implementation.
6. **Dialect placeholders:** constructs that databases spell differently become
   `{{handler(args)}}`, which the runner renders per database from the system file's
   `[dialect]` section (e.g. `{{seconds_between(a, b)}}`, `{{date_diff_days(a, b)}}`,
   `{{fetch_first(n)}}`). The handlers and their defaults: [RUNNER.md](RUNNER.md#dialects); where a
   difference goes: [DIALECTS.md](DIALECTS.md).

Queries are never rewritten around one engine's bugs; those count against the engine. Session
settings per system (e.g. DuckDB's `integer_division`, Umbra's `pgdatesub`) are in the system
files. Text collation is binary, by code point (Postgres needs `C.UTF-8`; see
[README.md](../README.md#loading-the-data)). Results are compared by value, not by text, in
query order (see [NUMERICS.md](NUMERICS.md#comparing-results)).

### Determinism review

The results are compared in order, so every query must be deterministic: its result may not
depend on how ties are broken. Umbra's indeterminism checker (reasoning with functional
dependencies) flagged 231 of the canonical queries; every flag was reviewed against the
schema's keys, and suspected false positives were confirmed by reducing the query until the
flag went away. Per-query verdicts and reasons: `workload/queries/determinism-review.json`.

- **139 queries could tie** under the schema and got a minimal tie-breaker (157 edits in
  `workload/queries/determinism.json`). Most end their ORDER BY with a name that is not a key
  (tenant, warehouse, supplier, product, user or agent names, coupon or template codes): the
  fix appends the entity's id. Others complete the grouping key, add a key inside a `FETCH
  FIRST` subquery or a window (`row_number`, `NTILE`, running sums), or add `ORDER BY` to a
  `string_agg`. 24 tie only by the letter of the schema: `calendar_days` declares only
  `calendar_date` as a key, so nothing forces `month_start` to determine `month_label`; these
  get the label column.
- **The other flagged queries are deterministic** and stay unchanged; the checker misses why
  (e.g. CASE ranks over a finite set of labels, a CHECK constraint, an OR in a join
  condition).
- **Results changed only where ties existed in the data:** q222 (which coupons make the
  `FETCH FIRST 20` cut), q153, and q155 (the order inside a `string_agg`).
