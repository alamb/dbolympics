Workload

The data is a deterministic simulation of Tidewick Commerce, a multi-tenant e-commerce platform: shops, orders, payments, shipping, support, marketing and more, in 251 tables. Shoppers, orders and events grow with the scale factor; the 120 merchants, their catalogs and the reference tables do not.

The data arrives over time. Every table is split into periods: everything through 2024 in one file, then one file per quarter of 2025.

The 409 queries were written by language-model agents role-playing Tidewick's managers, analysts and engineers over two simulated weeks. Each query can be traced to the conversation that led to it. They are standard SQL with a few placeholders where systems spell things differently (a year-month string, a difference of dates). Every query returns the same rows in the same order on every system; where needed, a tie-breaker was added.

Machines

Systems

Every system gets the same schema and the same queries. A system may change type names and the spellings behind the placeholders, and use its own settings to follow the standard, nothing else; foreign keys are never declared, and tables have no keys. How to add a system.

Supporting different SQL dialects

The agents were told to write standard SQL wherever possible. Some queries still use constructs outside the standard, and many systems do not support every standard construct. Each query therefore exists in two forms: the benchmark query, one text for all systems, and each system's version of it, in which the placeholders of the benchmark query are spelled the way that system needs. The following criteria decide which change goes where. The standard is SQL:2023; what is common is judged by the four most used relational databases in the Stack Overflow Developer Survey 2026 (PostgreSQL, SQLite, MySQL and SQL Server), not by the systems in the benchmark.

  • A query uses something the standard does not have, or relies on what the standard leaves implementation-defined.
    • If enough of the four support another way to write it, the benchmark query uses that: two of the four for a standard equivalent, three for any other operation. Examples: CAST(x AS DATE) instead of DATE(x), ROW_NUMBER() instead of DISTINCT ON, JSON_VALUE instead of ->>. What the standard leaves implementation-defined is written out: where NULLs go in every sort, tie-breakers.
    • Otherwise the benchmark query has a placeholder (listed below), and each system's version spells it.
  • A system rejects standard SQL.
    • If a simple equivalent exists in the system's dialect, the benchmark query marks the construct as a placeholder, with the standard construct as its default, and that system's version uses the equivalent. Simple means a fixed pattern at that place in the query that gives the standard's result for every input and can be applied by a simple textual match, without semantic analysis. If the equivalent costs nothing on any system, such as renaming an alias, the benchmark query uses it instead.
    • Otherwise the error stays, even where a larger rewrite would work.
  • A system runs standard SQL and returns something else.
    • If two of the four return the standard's result, the system is wrong, and its result stays.
    • Otherwise the four mostly disagree with the standard as well, and the benchmark query says explicitly what it means, as for the types and scales of numbers.

Systems may apply their own settings at startup to follow the standard more closely, such as DuckDB's integer division mode.

Every change from the SQL the agents wrote to the benchmark query is recorded, query by query. Each query's page shows these changes, and every system's version.

Procedure

For every machine and every system, starting from nothing:

  1. Start the system and wait until it answers.
  2. Create the schema, all tables at once.
  3. Load everything through the end of 2024: every table's file, all tables at once.
  4. Run all 409 queries {{REPS}}, in order.
  5. Load the next quarter and run all queries again, until all of 2025 is loaded: five loads, five rounds of queries.
  6. Check every result of the last round against the reference results.
  7. Stop the system and remove everything it wrote.

The system is never restarted during a run, so its caches stay warm, as they would in production.

A query over its timeout ({{TIMEOUT}}) is aborted and recorded as a timeout; it is skipped for the rest of that round and tried again after the next load. A query that fails is treated the same.

A run fails as a whole when the system runs out of memory, crashes, stops answering, or cannot load a file. The figures then show the run up to that point.

Isolation

  • One container group per run (a Podman pod): the system and anything it needs next to it, with no network to the outside.
  • Cores: every container is pinned to the machine's cores.
  • Memory: one limit for the whole group, counting everything, the file cache included, with no swap. A system that exceeds it is killed, and the run fails.
  • What the system sees: the limits, also through /proc, so that a system sizing itself from the hardware sizes itself to the limits.
  • The data is provided read-only, as Parquet files, with the list columns of four tables also as text for systems that need that. How a system loads it is up to the system; load time is measured, not prescribed.

Measures

Query time is measured by the benchmark, not reported by the system: from sending the query to having its whole result, over a connection that stays open for the run, so no client starts per query. {{REPS_COUNTS}}

Load time is measured the same way: from sending a load, every table's file of the period at once, to the system's answer that all of it is loaded. Creating the schema is timed apart and not counted.

Relative time (Table 1) is the geometric mean, over all 409 queries, of a query's time relative to the fastest correct system on that machine, both plus 10 ms so that the shortest queries do not dominate. A timed-out query counts as taking the full timeout ({{TIMEOUT}}); a failed one, one with a wrong result or one not run as taking twice the slowest correct time of that query on that machine (the timeout if no system answered it correctly).

Queries per second (Figure 1) is 409 over the time all queries take together after the last load (the median of each). A timed-out query counts as taking the full timeout, a failed or wrong one as taking twice the slowest correct time of that query.

Cost (Figure 1) is that same time at the machine's price per hour: what it costs to run all 409 queries once.

Efficiency (Figure 1) is queries per second (y-axis) divided by cost (x-axis). A system is efficient when it answers quickly without needing an expensive machine to do it: a bigger machine is worth it only if it makes the answers enough faster to justify its price. Looking at cost alone would favour a tiny machine that takes all day; looking at speed alone would always favour the biggest machine, whatever its price.

We measure efficiency by dividing queries per second by cost. Since both depend on how long the run takes, for ranking machines this comes down to one over price per hour × run time × run time. Chip designers use the same idea: the energy–delay product (Gonzalez and Horowitz, 1996). A chip run at a lower voltage uses less energy but computes more slowly. Judged by energy alone, the best chip would crawl at the lowest voltage; judged by speed alone, it would burn power at the highest. Multiplying energy by time finds the balance. For a database, the size of the machine plays the part of voltage, and the cost of the run the part of energy.

Another way to understand the metric is through Amdahl's law. No system scales perfectly with more resources, because some of its work cannot be split up. Say a system does 90 seconds of work that splits up easily across cores, and 10 seconds that does not, on machines priced by the core. On one core it takes 100 seconds, on 3 cores 40, on 9 cores 20. On 9 cores the split-up part takes 10 seconds, as long as the part that cannot be split, and that is where efficiency peaks. Before that point, more cores still shorten the run a lot; beyond it, the run mostly waits for the 10 seconds that no core can help with, and more cores add to the price far more than they take off the time.

Runtime distribution (Figure {{SEC_DISTRIBUTION}}) is, per system, the density of the times of the correct results after the last load (the median of each), on a log scale, estimated with a Gaussian kernel a tenth of a decade wide; its area is their share of all queries. The shares between the guides count the queries by band of time.

Correctness

Results are compared by value with reference results, row by row in order. The reference results come from Umbra with exact arithmetic, and at every scale factor match DuckDB on every query DuckDB answers.

  • Integers must match exactly.
  • Other numbers may differ by a small relative and absolute amount: |actual − expected| ≤ 0.0001 + 0.0001 × |expected| The queries do not round; the tolerance absorbs what SQL leaves to each engine, such as the scale of a quotient or the order in which floating-point numbers are added.
  • Timestamps may differ in trailing zeros, booleans in spelling, JSON in key order and spacing; NULL and the empty string count as equal.

Only the last round is checked; in earlier rounds a result counts as correct when the query finishes.

Use of AI

The queries were asked by language-model agents. In the role play, {{AI_AGENTS}} played every manager, analyst and engineer, and wrote the SQL. Every transcript is published with the queries.

The benchmark was built with an AI coding assistant. {{AI_WRITER}} designed the background story of Tidewick Commerce, the events that happen in it, and the data generation with its built-in skew.

Running the benchmark involves no AI. The data is generated deterministically, the 409 queries are fixed SQL, and results are checked against reference results. Nothing in it depends on a model or a vendor: any system that speaks SQL can run it.

Reproduce

Everything is in the repository: the generator, the queries, the reference results, the runner and the scripts for every system. On Linux with Podman:

cargo build --release --workspace
